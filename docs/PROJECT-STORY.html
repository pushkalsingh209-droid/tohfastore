What's inside

A catalogue worked by hand, sold online

Brass has been cast and polished by hand in India for centuries, aging into a warm patina that never quite looks the same twice. TOHFA brings that catalogue online: temple idols and diyas for the puja room, pocket-sized temples and pan-stand photo frames for a desk, corporate gifting sets for the festive season, and a scattering of polyresin décor, board games, and UV-resin jewelry for everything gifting touches that isn't strictly brass.

For the curious

Engineering notes

TOHFA runs on Next.js 16 and React 19, with Supabase (Postgres + Storage) for the database and Razorpay for payments — real, live payments, not a demo. WhatsApp messaging runs through the Green API, hosted on Vercel's free tier. Below are a few of the actual problems that came up building and running it — the kind of detail that doesn't make it into a product tour.

Caching

A sale doesn't invalidate the storefront

Every storefront read runs through Server Components hitting the database with a privileged key, wrapped in Next's unstable_cache and tagged by resource — products, categories, coupons. An admin edit calls revalidateTag and that tag's entries refetch on the next hit. A completed sale deliberately does not bust the products tag — firing that on every order would have scheduled a full-storefront regeneration per purchase. Stock and “N sold” are read live, client-side, instead, so the cached HTML can stand for a full day.

Infrastructure

The ISR quota fire drill

Product pages were originally statically generated with a 24-hour revalidate — one regeneration entry per product. That meant every deploy, and every product edit, regenerated all of them at once, and it quietly burned through 95% of the free hosting tier's monthly page-regeneration quota in a matter of weeks. The fix: render product pages dynamically, per request, over the same cached database reads — a product page still costs about 28ms of server time, just zero regeneration writes. Same speed for the shopper, a completely different cost profile for the host.

Payments

A payment can be reported twice

A successful order gets reported to the server twice, independently — once by a fire-and-forget call the browser makes the instant checkout succeeds, and again by the payment provider's own server-to-server webhook, which retries on its own schedule. Both hit the same handler; each has to survive the other firing first. A unique constraint on the payment id at the database level, checked before either path writes anything, is what actually makes “exactly once” true — not just “probably once.”

Security

Row-level security broke silently once

The public-facing database key ships inside every visitor's browser, so row-level security policies — not application code — are the real perimeter around orders, coupons, and anything else that shouldn't be world-readable. That perimeter was silently broken for months, once, by four leftover “allow everything” policies nobody remembered writing; database permissions are additive, so one forgotten permissive rule undoes every stricter one next to it. It's now re-asserted automatically, once a day, against the live database, with an alert the moment anything drifts again.

Inventory

Stock that (mostly) can't oversell

Stock only ever dropped after a payment cleared, which meant two shoppers could both successfully pay for the very last handmade piece before either checkout finished. A short-lived reservation now holds the requested quantity the moment checkout starts — one database function locks every line item, checks it against everything currently held by other in-progress checkouts, and grants the whole cart or none of it. Fifteen minutes, then it releases itself if the sale never completes.

Refactor

A 3,689-line file, tamed

The admin panel used to be one file: 3,689 lines, every tab's state and handlers tangled together in a single component. It's now seven lazily-loaded tabs sharing one context, and the file that's left is 231 lines of auth gate, data loading, and routing between them — nothing else.

Ongoing

Even free tiers have finite meters

The most recent tuning pass moved product-card thumbnails onto their own pre-generated, purpose-sized image instead of quietly shipping the full-resolution original to every card on every page load — one of a running list of small, deliberate trade-offs that keep a one-person storefront comfortable on infrastructure built for hobby projects.

Craft & process
Type safety

39 bugs the compiler found before anyone did

Every database client is generated straight from the live schema, which turned a whole class of silent bugs into compile errors instead: ids quietly compared as strings against a numeric column, JSON columns read as untyped blobs, nullable fields treated as guaranteed. Regenerating those types is now a required step after every schema change — a stale one fails the build outright, rather than failing quietly at 2am.

Testing

Payment code doesn't ship on faith

Around 110 unit tests cover the parts that are expensive to get wrong — GST and discount math, signature verification, one-time codes, cart re-pricing, stock-reservation availability. The order-normalization tests include a deliberate round-trip check: feed it a well-formed order and assert the output comes back byte-for-byte identical, so a “safety” refactor can't quietly start mutating orders that were already fine. Anything touching the payment path is treated as a proposal, not a done thing, until it's been watched against real orders.

Code quality

Zero shortcuts on the type checker

The codebase went from 246 lint problems — roughly 135 of them genuine errors — down to zero errors, and untyped any usage from 174 occurrences to none. Not by silencing the rule: by writing out the actual shape of every admin payload, cart item, and webhook body. The handful of warnings still left on purpose each carry a comment explaining exactly why they're false positives, rather than being suppressed and forgotten.

Process

No change ships undocumented

Every batch of work follows the same loop: make the change, verify it — typecheck, the full test suite, a real production build — update the reference documentation and write a dated changelog entry, and only then open it for review. Documentation is a precondition for shipping, not a follow-up task. The main branch is protected: nothing merges without that verification passing first, and changes are worked one at a time so two in-flight batches can never quietly overwrite each other's notes.

Observability

The system tells on itself

Scheduled jobs stamp a heartbeat every time they run; if one goes quiet, an admin dashboard card turns amber instead of the failure being discovered a week later from a customer complaint. An automated check re-asserts the entire security perimeter against the live database every day and raises an alert the instant anything drifts — the same class of issue that, once, went unnoticed for months.

Comments

Comments explain the why, not the what

The codebase is deliberately over-commented in one specific way — not describing what a line does, but why it exists: the alternative that was rejected, the race condition being avoided, the cost trade-off behind a setting. A new non-obvious decision doesn't ship without a line naming what it deliberately isn't doing, and why.
