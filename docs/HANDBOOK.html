Shape of the system

Design decisions & the why

Server reads are cached; writes and live reads are not

Storefront reads run in Server Components against supabaseAdmin (service role), wrapped in unstable_cache (app/utils/storeQueries.ts) with tags and a 24 h revalidate. Writes, third-party calls, and genuinely-live reads (stock) are Route Handlers. "server-only" guards the service-role client so it can never reach the browser bundle.

RLS is the security perimeter

The Supabase anon/publishable key ships in every visitor's JS. So Row Level Security — not application code — is what actually protects data. Because the admin panel goes through password-gated /api/admin/* routes on the service role, the anon key can be (and is) locked right down: orders, coupons, leads, admin sessions unreadable; hidden products and unapproved reviews unreadable; no anon writes. A scheduled probe (/api/cron/rls-check) re-asserts this against the live project daily and WhatsApps the business on any drift — this exact perimeter was silently broken for months once by four stray policies.

Never trust the client at checkout

Server-side, every time: re-price from the DB, re-validate the coupon, re-check stock and the hidden flag, re-verify the WhatsApp OTP token. The item list, coupon, verified phone, customer name and shipping address are read back from the Razorpay order notes the server wrote at creation time — a tampered request can't claim a different, larger basket after paying.

Best-effort side effects never block the action

WhatsApp / email / analytics sends are try/catch + console.error. A missing key or a failed send is logged and swallowed — the order is still recorded, the status still changes. Follow this pattern for anything non-critical.

Fail closed on security config

Missing ADMIN_PASSWORD or ADMIN_TOTP_SECRET → the route 500s. No silent fallback to a default. 5xx bodies are generic (serverErrorResponse); the real error is logged, never echoed. 4xx validation messages are user-facing and fine.

Payments are idempotent by construction

/api/razorpay-webhook has two callers — the client fast-path (fires right after the Razorpay modal succeeds, for a quicker confirmation) and Razorpay's own Dashboard webhook (independent retries). Both are verified with the scheme appropriate to what that caller holds. A SELECT payment_id check plus a UNIQUE(payment_id) constraint (migration 0037) means a duplicate call — from either path, in any order — can't insert a second order or deduct stock twice.

Two deliberate Hobby-plan choices — do not "fix" them

  • /product/[id] and /api/stock/[id] are force-dynamic. Product pages were SSG with generateStaticParams for ~156 products; every deploy and every revalidateTag("products") regenerated all of them and hit 95% of the Hobby ISR-write quota. Profiling since shows a product page renders in ~28 ms of CPU because its data is still unstable_cached — so dynamic rendering costs almost nothing and writes nothing.
  • images.unoptimized: true in next.config.ts — protects the Hobby image-optimization meter. Small-thumbnail contexts (cart, wishlist, admin list) use a build-time -thumb.webp variant via attachThumbUrls instead.

Both are reversible one-liners if the plan changes for good — but the default is Hobby-ready.

The system watches itself

A keepalive heartbeat (keeps the Green API instance warm, stamps a timestamp), the RLS probe, and a product_sales reconcile job all run on an external scheduler and WhatsApp the business on failure. Staleness of each is surfaced as an amber card on the admin Overview tab, so a dead scheduler shows on the dashboard instead of failing silent.

How work gets done

Every multi-change piece of work follows one loop: batch → verify → document → deploy → recommend. One PR open at a time — finish it, merge, git checkout main && git pull, delete the branch, then start the next. main is branch-protected; a direct push is rejected and CI's verify check (tsc + npm test + next build) must pass. Documentation (this handbook's Architecture + Change Log tabs — affected sections + a dated Change-log row) is updated before the merge, never after. Full detail on the Developer Guide tab.

Cost / liability guardrail Nothing that incurs a paid service or plan, and nothing that changes the payment / order / webhook path in a way that could lose orders, double-charge, or mis-refund, ships without an explicit owner go-ahead. These are flagged 💰 / ⚠ in IMPROVEMENTS.md.

Code FlowsHow a request actually moves through the code

Eight walkthroughs, source-of-truth files named at each step. Read alongside the route table and checkout section in the Architecture tab.

Flows: 1 Storefront render · 2 Product detail · 3 Cart → 3-step checkout · 4 Create payment · 5 Payment webhook · 6 Admin save → cache bust · 7 Reservation lifecycle · 8 Scheduled jobs

1  Storefront render  RSC

/ and /collections/[category] both render through app/components/StorefrontPage.tsx (an async Server Component).

  1. Bootstrap + catalog in parallel. Promise.all over getHiddenCategoryNames, getPublicCoupons, getCategorySliderItems, getTotalProductCount, getBestsellers, getSiteSettings, getActiveLabelNames — all unstable_cached (app/utils/storeQueries.ts), tag products / categories / site-settings, 24 h revalidate.
  2. Page + page size. An explicit visitor ?pageSize= wins; else the category's own override; else the site-wide default.
  3. The listing. getCatalogPage(page, pageSize, category, sort, hiddenCategories, inStockOnly, label) — one indexed count, one ranged SELECT of only the ~17 columns a card renders, then attachThumbUrls + getSoldCounts (also cached).
  4. Client hand-off. Products go to CatalogSection (client) which reveals cards in batches as the shopper scrolls and unmounts far-off-screen cards to bound decoded-image count.
  5. Per-card live stock. Each ProductCard's LiveStock child fetches /api/stock/[id] on mount — the one figure that must never be stale.

2  Product detail  force-dynamic

  1. Param. The route param is <id>-<slug>; productIdFromParam extracts the id. A bare or stale slug → permanentRedirect to the canonical URL.
  2. Fetch. getProduct(id) (unstable_cache, tag products). Returns null if name or price is null; hidden or missing → a "not found" body.
  3. Render. Gallery, breadcrumbs, JSON-LD, related products (getRelatedProducts). Live stock & recent-viewer count are fetched client-side.

3  Cart → 3-step checkout

  1. Cart. CartContext (localStorage-backed) → CartDrawer shows the bag; "Proceed to Checkout" mounts CheckoutSheet, which takes over the drawer.
  2. Contact step. Name / email / phone, then WhatsApp OTP: POST /api/whatsapp-otp/send → POST /api/whatsapp-otp/verify returns a short-lived token. A one-time checkout_started lead beacon fires per phone.
  3. Delivery step. Pincode-first address form.
  4. Review step. Collapsible order summary, coupon field with a tap-to-apply list of live public coupons (GET /api/coupons/public), bilingual cancellation/refund consent (required). While the storewide Spend & Save tier offer is running (GET /api/offer), a two-option selector appears above the coupon UI — Use offer (₹X off / "add ₹Y more to save ₹Z") vs Use a coupon — and the shopper picks one (mutually exclusive, never stacked; default "offer"). discountChoice ("offer" | "coupon") is sent to Flow 4.
  5. Pay. The sheet footer button calls handleRazorpayPayment → Flow 4.

4  Create payment  POST /api/razorpay

  1. Re-price. repriceCart(clientItems, dbProducts, categoryGstRates) — price, GST rate, category and image come from the DB row, not the request. Any item no longer available → 400.
  2. Discount (authoritative). Offer and coupon are mutually exclusive — the body's discountChoice ("offer" | "coupon" | absent) says which the shopper picked, and this route re-validates only that one. discountChoice==="coupon" → coupon path even while the offer is live; "offer" → the tier discount for the re-priced subtotal (calculateSpendTierDiscount off site_settings.spend_tier_offer, parseSpendTierOffer fail-closed), 0 if the offer turned out inactive server-side (not an error); absent → the pre-choice default (offer wins while active, coupon otherwise). Stock and hidden re-checked. OTP token re-verified.
  3. Reserve (if enabled). If site_settings.stock_reservations_enabled === '1': checkoutToken = randomUUID(), then reserve_stock(token, pricedItems, 900). Not enough stock → 400 stock_unavailable; RPC error → 500 (fail closed).
  4. Create the Razorpay order with server-authored notes: items (JSON), couponCode, offerLabel (Spend & Save label if applied; display only), verifiedPhone, checkoutToken, customerName, shippingAddress. Return { orderId, subtotal, discount, couponCode, offerLabel, gst, checkoutToken }. The webhook still derives the discount itself as subtotal − captured total, so its GST split and the invoice already handle the tier discount with no change.
  5. Client opens the Razorpay modal with that orderId. On success it fires the webhook fast-path and redirects to /success. On dismiss/failure it calls POST /api/checkout/release with the token and returns to the review step.

5  Payment webhook  POST /api/razorpay-webhook payment path

  1. Tell the callers apart. An x-razorpay-signature header → Dashboard webhook, verify the webhook HMAC. No header → client fast-path, verify the payment signature. Missing/invalid → 401.
  2. Idempotency. SELECT id FROM orders WHERE payment_id = ? → already recorded, return early.
  3. Trust nothing from the body. razorpay.payments.fetch + orders.fetch. Confirm status === "captured" and the order id matches. Read items / coupon / verified phone / name / address from the order notes.
  4. Normalise the items. normalizeOrderItems(notes.items) — every entry coerced to finite price/quantity and a real per-item gstRate before any total is computed. A well-formed note is returned unchanged (8 unit tests pin this).
  5. Insert the order. Unique payment_id violation (23505) → lost the race, already recorded, done.
  6. Coupon. If one was used, used_count + 1 and revalidateTag("coupons").
  7. Deduct stock. With a checkoutToken: consume_reservation(token) (row-locks each product, decrements clamped at 0, marks the hold consumed, returns per-line new_inventory / oversold_by). No live hold → fall through to the legacy per-item decrement_inventory loop (migration 0041). Oversell / low-stock alerts fire from the returned rows.
  8. Units-sold tally. apply_product_sales(items, +1) (migration 0042).
  9. Notify. Build the summary once; send business + customer WhatsApp (with a hero image) and both Resend emails. All best-effort — a failure logs and is swallowed.
  10. Supplier copies (0046). Resolve products.supplier_numbers for this order's items against the live order_notification_numbers list (resolveSupplierTargets): the unioned set gets the same business order message; each product's own set is copied on that product's low-stock / oversell alert. Best-effort, Promise.allSettled, never blocks.
Deliberately absent No revalidateTag("products") or "orders") here. Those tags are read on every product and catalog page, so firing them per sale scheduled a full-storefront regeneration — the single biggest source of metered ISR writes. "N sold" and the bestsellers strip are fine slightly stale and refresh on their own 24 h window; live stock is read client-side per request.

6  Admin save → cache bust

  1. The panel never talks to Supabase directly. A tab calls apiRequest("/api/admin/…", { method }) (app/admin/lib/apiRequest.ts); the route is password-gated by middleware.ts and uses the service role.
  2. Write to Postgres.
  3. Invalidate — revalidateTag("products" | "categories" | "coupons" | "reviews" | "site-settings" | "labels", "max"). The storefront's Data Cache entry for that tag is rebuilt on the next read (a cheap refetch — not an ISR page regeneration on the dynamic routes).
  4. Local state. The tab updates its slice of AdminDataContext (or calls refetch) so the panel reflects the change without a reload.
Do not do this "Do a trivial admin save to bust the cache" is not a valid fix for a stale storefront — each such save fires revalidateTag("products"). When product pages were SSG that regenerated ~156 pages per save and helped push the ISR-write meter to 95%.

Code style — match the surrounding file

  • Comments carry the why. This codebase is densely commented with the reasoning behind non-obvious choices (cost trade-offs, race windows, "deliberately not X"). A new non-obvious decision gets a comment naming the alternative you rejected.
  • Server vs client. Storefront reads → Server Components + supabaseAdmin + unstable_cache. Writes / third-party / live reads → Route Handlers. "server-only" guards the service-role client.
  • Best-effort side effects → try/catch + log, never block.
  • Fail closed on security config — missing secret → 500, no default.
  • Never trust the client at checkout — re-price, re-validate, re-check, server-side.
  • Shared constants over "keep in sync" comments (e.g. app/utils/stock.ts).
  • 5xx bodies are generic — serverErrorResponse from app/utils/apiError.ts; log the real error, don't echo it. 4xx validation messages are user-facing and fine.
  • TypeScript strict; path alias @/* → repo root (mirrored in vitest.config.ts). Tailwind v4; class-based dark mode.
  • Docs are self-contained — this handbook stays CDN-free: system fonts, inline SVG, zero scripts, no external assets. The tab nav is pure CSS (:target + :has()).

The working agreement — batch → verify → document → deploy → recommend

  1. Batch. Group related changes, keep the diff surgical. One PR at a time. Finish a batch, push its branch, wait for merge, then git checkout main && git pull and delete the branch before the next. Never two PRs open (they collide at the top of IMPROVEMENTS.md and the Change-log table).
  2. Verify. npx next build (exit 0), npx tsc --noEmit, npm test, npx eslint <changed> (no new errors vs. the 0-error / 28-warning baseline). Report the real results. A payment-path change with no live Razorpay is a proposal, not done.
  3. Document — this GATES the deploy. Before merging: update this handbook — the affected part of the Architecture tab, a new dated row at the top of the Change Log tab (date/time IST, files touched, how verified), and any flow or guide that changed. Re-publish the artifact. Move shipped items to Done in IMPROVEMENTS.md.
  4. Deploy (only on the owner's word, only after step 3). main is branch-protected — push the branch, open a PR, wait for the verify check (CI: tsc + npm test + next build), re-verify the merged HEAD, merge. Then sync main and delete the branch.
  5. Recommend. End with a short prioritised "what next" — new issues, deferrals, follow-ups. Durable ones go into IMPROVEMENTS.md.

Playbooks

Add a storefront read

New function in app/utils/storeQueries.ts, wrapped in unstable_cache with the right tag and a revalidate. Narrow the select(...) to the columns actually rendered — not select("*"). Consuming Server Component just awaits it.

Add an admin write

app/api/admin/<thing>/route.ts, service role, do the write, then revalidateTag(<tag>, "max"). The tab calls it through apiRequest and updates its context slice (or calls refetch).

Add a migration

supabase/migrations/NNNN_name.sql, hand-run in order. Grant gotcha: revoke … from public on a SECURITY DEFINER function also strips service_role's inherited grant — you must grant execute … to service_role explicitly (see 0041/0042/0043). Then update ARCHITECTURE's schema/migrations section + a Change-log row, and run npm run gen:types.

Add a site setting

A key in site_settings; a parser in app/utils/bootstrapSettings.ts (with a test); a field in the admin Settings tab; the write route calls revalidateTag("site-settings"). Read it from getSiteSettings() / BootstrapProvider, never process.env.

Structured setting (a list, not a scalar): store one JSON string under one key and give it a dedicated pure module — e.g. spend_tier_offer → app/utils/spendTierOffer.ts with a lenient, fail-closed parse…() for the read paths and a strict sanitize…() (returns errors) for the admin PATCH branch. Unit-test the module the way coupons.ts/gst.ts are. A tiny NNNN_seed_….sql (on conflict do nothing) records it in the migrations trail.

Add an admin tab

Add the key to ADMIN_TABS in app/admin/page.tsx + a { key, label } nav entry. The tab is app/admin/tabs/<Key>Tab.tsx (default export), const XTab = dynamic(() => import(…), { ssr:false }) at the page's module top, rendered as {activeTab === "<key>" && <XTab />}. Shared data still loads in loadAll(); the tab reads its slice via useAdminData() (add the field to AdminData and the provider value). Tab-local state (form drafts, filters) lives in the tab.

Add a cron route

app/api/cron/<name>/route.ts, GET, gate on Authorization: Bearer CRON_SECRET when set, export const dynamic = "force-dynamic". Vercel Hobby cron caps at 2 — document that an external scheduler (cron-job.org) must hit it. Stamp a site_settings heartbeat and surface staleness on admin Overview (pattern: the keepalive card).

Add a request-independent image/OG route

Next 15+ defaults a GET route handler to dynamic. If the output never varies by request (icons, splash screens, static OG), add export const dynamic = "force-static" (+ generateStaticParams for a dynamic segment) so it rasters once at build, not per hit.

Gotchas

  • Data Cache ≠ ISR writes. unstable_cache uses the Vercel Data Cache — a large, cheap meter. ISR writes (page regeneration) are the tight Hobby meter, and why /product/[id] is force-dynamic.
  • Postgres grant gotcha (see the migration playbook above).
  • CRLF + node fs. Files on disk have CRLF; a multi-line "\n"-joined search string in .replace() via readFileSync silently won't match. Use editor edits or single-line replacements.
  • react-hooks/set-state-in-effect is downgraded to warn — it flags the standard Next-SSR "hydrate from localStorage / cookie / matchMedia on mount" pattern, which is not the cascading-render bug. Kept visible, not silenced.
  • Two intentional eslint-disables with rationale: CatalogSection reads a measured-height ref during render (a placeholder cache that must not trigger re-renders); StorefrontPage's Math.random() hero pick (a per-request rotation in an RSC that never hydrates).
  • Next.js is not the one you know — APIs and conventions differ from older versions. Read the guide in node_modules/next/dist/docs/ before writing route/convention code.

Observability

  • Vercel → Observability → Functions — per-route Active CPU, invocations, P75 duration, cold-start %. Logs tab for runtime logs (Pro; short retention on Hobby).
  • Axiom — a Vercel log drain into the vercel dataset (~30-day retention, survives a Hobby downgrade). Query with APL, e.g. ['vercel'] | where level == "error"; Stream for live tail.
  • Supabase → Logs → Explorer — SQL over Postgres / auth / PostgREST / edge logs. Free, zero setup.
  • The app's own signals: the three Overview heartbeat cards, and the RLS / reconcile / oversell / low-stock / Green-API-down WhatsApp alerts.

Orders

List, search, filter by status. Change a status, set an AWB / tracking number, and pick the delivery partner (dropdown of common couriers + “Other…”) — all saved silently, no message goes out. When you're ready, hit Notify customer on that row: a dialog shows a preview of the message for the order's current status, lets you add an optional one-off note, and sends it by WhatsApp + email. Works for every status (a "your order was cancelled" note, a "running a day late" heads-up, etc.). Courier + tracking also show on the public /track page and the invoice. The first time you send a Delivered notification for a customer, it also mints (or reuses) their personal referral coupon and appends it to the message — see the Coupons card below.

After refunding a test order Set its status to Cancelled. A cancelled order is excluded from analytics, bestsellers, and the units-sold tally — so your real numbers stay clean.

Coupons

Create flat or percent coupons with a max-uses cap and an expiry; toggle active; toggle "show on site" (a public coupon appears in the checkout's tap-to-apply list). used_count only increments on a verified, paid order — an abandoned checkout never burns a redemption. While the Spend & Save offer (Settings tab) is switched on, the checkout shows the shopper a choice — use the offer or a coupon, one or the other, never both on the same order.

Referral coupons appear in this same list, auto-created (default 10% off, 90-day expiry — both admin-editable, see below — one per customer) the first time an order's Delivered notification goes out — not at payment time, so a cancelled/refunded first order never earns one. They're ordinary coupon rows (a referral_phone column marks them) and show up here like any other. The owning customer can't redeem their own code — /api/razorpay checks the checkout's OTP-verified phone against it and rejects a self-redemption.

Stock reservation

site_settings.stock_reservations_enabled = '1' turns on the 15-minute hold at checkout (migration 0043). A checkout holds its items; the webhook consumes the hold (that's when inventory actually drops); a dismissed/failed payment releases it; an abandoned one expires and is trimmed by the daily cron. This is what stops two shoppers buying the same one-off piece during a rush. To check it's on:

select value from site_settings where key = 'stock_reservations_enabled';  -- want '1'

High-level architecture

Rendering & data model

  • Server Components do all storefront data fetching directly against Supabase using the service-role client (app/utils/supabaseAdmin.ts), wrapped in unstable_cache (app/utils/storeQueries.ts).
  • Route Handlers (app/api/**/route.ts) handle every write, every third-party call (Razorpay, Green API, Resend, India Post PIN lookup), and the reads the browser needs live/uncached.
  • Client Components hold ephemeral UI state (cart, wishlist, drawers) and fetch live stock / recent-viewer counts on mount so statically-rendered pages can be cached for a day.
  • The browser never touches orders / coupons — RLS denies it; everything goes through server routes.

Order lifecycle (text)

CartDrawer (client)
  1. POST /api/whatsapp-otp/send   {phone}                -> Green API sends 6-digit code
  2. POST /api/whatsapp-otp/verify {phone,code}           -> returns single-use verificationToken
     (also POST /api/leads {source:"checkout_started"} for abandoned-cart tracking)
  3. POST /api/razorpay {items, couponCode, phone, whatsappVerificationToken, customerName, shippingAddress}
        - server re-prices every item from DB (ignores client prices)
        - re-validates coupon, re-checks stock + hidden, re-checks isVerificationTokenValid()
        - Razorpay order created; verifiedPhone + items + customerName + shippingAddress pinned into order.notes
  4. Razorpay checkout.js modal opens; customer pays
  5. handler(): fire-and-forget POST /api/razorpay-webhook + stash summary in sessionStorage -> /success
/success: clearCart(); fire GA4 + Meta "purchase" (deduped in localStorage by orderId)

Row Level Security model

The publishable/anon key ships in every visitor’s JS bundle, so RLS is the real perimeter for direct-to-Supabase reads. Final effective state (migrations 0003 → 0039 → 0040 → 0047):

TableAnon key — readAnon key — writeService role
productsyes, where hidden = falsenofull (bypasses RLS)
reviewsyes, where approved = truenofull
ordersno policy → deniednofull
couponsno policy → deniednofull
site_settingsno policy → denied (RLS on since 0047)nofull
every other tableno policy → deniednofull

Regression guard (two layers, one probe set in app/utils/rlsProbes.ts): rls.test.ts fails CI on a regression; /api/cron/rls-check runs the same anon-key probes against the LIVE project on a daily external schedule and WhatsApps the business on any violation — so a policy edited in the Supabase dashboard after deploy surfaces in hours. Both connect with the anon key and assert this table — run it (with .env.local exported) after any schema or policy change, and keep it in CI. It skips cleanly when Supabase creds are absent.

History / lesson (0039, 0040): the original lockdown (0003) was effectively a no-op because four stray dashboard-generated policies (products, orders, forreviews, forcoupons) existed as FOR ALL … USING (true). Postgres RLS is permissive-OR across policies, so one ALL/true policy grants unrestricted CRUD regardless of any stricter policy. 0040 drops them. After any schema change, verify with select * from pg_policies that no stray permissive policy exists.

Second instance (0011, 0047): site_settings was created in 0011 with no enable row level security line — the only table migration that missed it — so the anon key could read and write every KV row (pricing, the Spend & Save offer, feature kill switches) for ~36 migrations, until Supabase's advisor flagged rls_disabled_in_public. 0047 turns it on (no policy). The lesson: every create table migration must include its RLS line, and rlsProbes.ts now covers site_settings read + write.

with recomputed as (
  select (i->>'id')::bigint as pid,
         sum(coalesce((i->>'quantity')::int, 0)) as units
  from orders o
  cross join lateral jsonb_array_elements(coalesce(o.items, '[]'::jsonb)) i
  where o.status <> 'cancelled' and (i->>'id') ~ '^\d+
  group by 1
)

       coalesce(r.units, 0) as should_be,
       coalesce(ps.units_sold, 0) as stored
from recomputed r

where coalesce(r.units, 0) <> coalesce(ps.units_sold, 0);

Checkout & payments flow

The bag lives in app/components/CartDrawer.tsx (code-split via LazyCartDrawer) — since #17c (2026-08-30) that file is only the bag list + a “Proceed to Checkout” button (~150 lines, was ~1,220). That button opens app/components/checkout/CheckoutSheet.tsx, a 3-step sheet that replaces the whole drawer and is the only checkout path. (17b did the cutover behind a NEXT_PUBLIC_LEGACY_CHECKOUT env fallback; 17c deleted the old inline single-form path and the flag once the new flow had clean live orders.)

Structure

  • useCheckoutMachine.ts (#17a) — a pure useReducer. Its phase is the step: contact → delivery → review, then paying → razorpayOpen while the modal is up. It holds only the phase, the OTP sub-state, the resend cooldown, and the {token, phone} pair once verified — never the typed field values, so a Back nav or a verification_required rewind can’t clear them. Unit-tested (useCheckoutMachine.test.ts, 18 cases).
  • CheckoutSheet.tsx owns every typed value (name/email/phone, OTP code, address, coupon, policy consent) and the payment orchestration. Renders Stepper + one of steps/{ContactStep,DeliveryStep,ReviewStep}. Each step component is a near-verbatim lift of the old CartDrawer JSX; each owns its own input refs and self-manages focus.
  • Stepper.tsx — sticky header: Back chevron (never loses input) + step title + 3-segment progress bar + “Step N of 3”.

Step 1 — Contact & Verify

  • Name, email, WhatsApp number.
  • On a valid 10-digit number, POST /api/check-whatsapp-number live-validates registration (valid/invalid/unknown). unknown (Green API off) still lets checkout proceed; invalid clears the field. A phone edit runs PHONE_CHANGED — drops any verification.
  • OTP gate: /api/whatsapp-otp/send → user enters code → /api/whatsapp-otp/verify → the reducer stores the returned single-use token in state.verified. 45s resend cooldown ticked by the machine, surfaced in the UI.
  • The Continue footer button is disabled until m.contactVerified is genuinely true.
  • On successful verify, fire-and-forget POST /api/leads {source:"checkout_started", details:{cartItems,cartTotal}} (once per verified phone) so an abandoned checkout is recoverable (§21 cron).

Step 2 — Delivery

  • PIN first in the DOM — 6 digits → debounced /api/pincode/[code] auto-fills city/state (both stay editable). Then address line, landmark (optional), city, state dropdown (INDIAN_STATES).
  • validateDelivery() (pincode / address / city / state) gates the Continue button.
  • Receiver’s phone (optional, added post-0049) — a gift-order field: only fill it when the parcel is going to someone other than the buyer, so the courier has a number to call at the delivery address. Free text, no format check, never gates Continue — purely informational, distinct from the buyer's own OTP-verified phone. Stored as shippingAddress.recipientPhone.

Step 3 — Review & Pay

  • Collapsible order summary — line items, MRP subtotal, per-category GST line, coupon line, grand total (same math as the old footer).
  • Coupon field → /api/coupons/validate (preview only), plus a tap-to-apply list of the live public coupons from GET /api/coupons/public (hidden once one is applied).
  • Spend & Save offer (useSpendTierOffer → GET /api/offer): while it's running, a two-option selector sits above the coupon UI — Use offer (tier discount off the current cart, or an "add ₹X more to save ₹Y" nudge) vs Use a coupon (reveals the normal coupon UI). Local discountChoice state, default "offer"; removing an applied coupon flips it back. Only the chosen one is sent to POST /api/razorpay (as discountChoice + couponCode when relevant). The /success stash takes subtotal/discount/couponCode/offerLabel from the server response, not client guesses.
  • Mandatory bilingual refund-policy consent checkbox — the footer Pay ₹X button is disabled until it’s ticked.
  • Pay: m.submitPayment() → POST /api/razorpay. On code:"verification_required" → m.verificationExpired() (back to step 1). On code:"stock_unavailable" or any other non-orderId error → m.paymentDismissed() (stay on Review, show the message). Otherwise open the Razorpay modal (orderId/amount), m.razorpayOpened(). The response’s checkoutToken (present only when reservations are on) is held in a local; the modal’s ondismiss and a rzp.on("payment.failed") handler both run m.paymentDismissed() + fire-and-forget POST /api/checkout/release with it.
  • handler(): fire-and-forget POST /api/razorpay-webhook (client fast path), stash the server-computed summary (incl. gst) in sessionStorage.tohfa_last_order, m.reset(), close the drawer, redirect to /success. Byte-for-byte the old body.

Server-side guarantees (never trust the client)

  • Every line item re-priced from products by id; unknown/hidden id → reject “no longer available”. (Pure + unit-tested: repriceCart in app/utils/repricing.ts.)
  • Quantity > stock → reject (not silently clamped).
  • Stock reservation (0043, when enabled): before a payable order exists, reserve_stock row-locks each product and checks inventory − Σ(held, unexpired holds) ≥ qty, all-or-nothing for a multi-item cart. A second checkout for the last unit gets 400 stock_unavailable and never reaches Razorpay. Holds TTL out in 15 min; the webhook consumes the hold on payment. Does not eliminate oversell — a payment that lands after its hold expired still records + fires sendOversellAlert, exactly as before — it closes the checkout-vs-checkout race. Off → behaviour is exactly as before.
  • Discount — offer and coupon are mutually exclusive; the client's discountChoice selects which, the server re-validates only that one from site_settings.spend_tier_offer / the coupons table (never trusting the client's amount), clamped to [0, subtotal].
  • GST computed per item’s category rate (calculateOrderGstBreakdown), discount spread proportionally across rate groups.
  • OTP: isVerificationTokenValid(phone, token) requires the exact token minted for that verification, still within its 60-min window — knowing an already-verified number is not enough.
  • Webhook re-fetches razorpay.payments.fetch + razorpay.orders.fetch; requires status === "captured" and order_id match; reads the pinned order.notes.

Caching & performance

The most deliberately-engineered part of the codebase. Constraints: Vercel Hobby meters ISR writes (every background regeneration, tag-triggered or not) and Image Optimization transforms; Supabase free tier meters API requests and auto-pauses after 7 idle days.

Cached reads — app/utils/storeQueries.ts

  • Every visitor-invariant read is wrapped in unstable_cache([...key], { tags, revalidate: 86400 }). Uniform 24h window — only a safety net; freshness comes from on-demand revalidateTag.

Security model summary

  • RLS — the browser’s publishable key can only read non-hidden products and approved reviews; nothing else, no writes (§6).
  • All writes & secrets server-side — service-role key is server-only; Razorpay secret, Green API token, Resend key, admin password/TOTP never reach the client.
  • Payment integrity — server re-prices from DB, re-validates coupon, re-checks stock; webhook re-fetches from Razorpay and verifies HMAC signatures (two schemes); order idempotency at app + DB level.
  • Checkout identity — WhatsApp OTP with a single-use per-session token; the verified number is pinned server-side into order.notes (client can’t edit it afterward), overriding Razorpay’s editable payment.contact.
  • Admin auth — password (constant-time) + TOTP/backup-code, DB-backed revocable 12h sessions, per-IP login rate limit, fail-closed on missing config, “log out everywhere”.
  • Admin CSRF — (working branch) proxy.ts rejects a mutating method on /api/admin/* whose Origin header is cross-host, on top of the sameSite:lax cookie.
  • Abuse limits — DB-backed per-IP rate limiting on every public POST (rate_limit_events), OTP send/verify caps, contact-form honeypot. Log tables self-prune.
  • Order tracking — needs reference AND matching phone; user input never interpolated into PostgREST filter strings.
  • Error hygiene — every route under app/api (storefront, admin, cron, webhook) returns a generic 5xx body via serverErrorResponse (apiError.ts); the real exception / Postgres text is logged server-side, never echoed. No catch (err: any) in app/api feeds a 5xx any more. 4xx validation messages are untouched (they are written for the user and safe).
  • RLS regression test — app/utils/rls.test.ts connects with the anon key and asserts the §6 perimeter (no orders/coupons/hidden-product/unapproved-review reads, no writes). Env-gated; run it after any schema or policy change.
  • Headers / CSP — next.config.ts sets (production only) a Content-Security-Policy (explicit allow-list for Razorpay / GA / GTM / Meta / Google Translate / Supabase), X-Content-Type-Options, Referrer-Policy, Permissions-Policy (payment=(self), everything else denied), X-Frame-Options: SAMEORIGIN.
  • JSON-LD XSS — < escaped to its unicode form in every <script type="application/ld+json">.

Known constraints & gotchas

  • Image Optimization is off (images.unoptimized = true) as a temporary quota safety net. Re-enable and re-check after the billing cycle resets.
  • Every route streams because of the root app/loading.tsx; that’s why proxy.ts exists to emit real HTTP status codes. Remove loading.tsx and the page-level redirect()/notFound() calls become sufficient on their own.
  • The webhook intentionally does not revalidateTag("products"/"orders") after a sale — a cost decision, not an oversight. Stock is live client-side; sold counts / bestsellers accept 24h staleness (see the §16 diagram).
  • Post-sale stock deduction is now race-free (2026-08-29) — the webhook calls decrement_inventory() (migration 0041, SELECT … FOR UPDATE row lock) instead of a per-item read-modify-write, so two webhooks for the same product serialise. oversold_by > 0 fires a business “OVERSELL” WhatsApp. Residual: stock is still only decremented post-payment, so two checkouts for the last unit can both pay and one order is then flagged oversold rather than prevented — a short-TTL stock reservation at order creation would close that window (IMPROVEMENTS.md). Also owed: one live test payment to confirm the RPC path end-to-end.
  • Sold-count accuracy past ~300 orders — getSoldCounts now reads the incremental product_sales aggregate (migration 0042), so the customer-facing “N sold” count is exact regardless of lifetime volume. getBestsellers / getRelatedProducts still scan only the last 300 orders — deliberate: they rank relative popularity, where the 300-order horizon is immaterial. (Live since 2026-08-29; webhook +1 / cancel −1 hooks verified end-to-end against the production DB. The tally can still drift if an order is cancelled outside the admin update-status route — run the §7 drift-scan query to catch it.)
  • Admin product routes silently drop unknown columns and retry (insert/updateWithFallback) — a save can partially succeed if a migration hasn’t been run; the response flags which fields were saved (gallerySaved, hiddenSaved, …).
  • Base tables (products, orders) were dashboard-created — supabase/migrations/0000_base_schema.sql (added 2026-08-29) reconstructs them so a fresh project can be bootstrapped from the folder. IF NOT EXISTS-guarded (no-op on prod). Verified against live 2026-08-29 via information_schema introspection — the pre-0001 column subset now matches prod exactly. Corrections vs the first guess: identity is BY DEFAULT not ALWAYS; products.images is text[] not jsonb; products.inventory is bigint nullable no-default; products.name/price and orders.order_id/payment_id/amount are all nullable. The dashboard tables are permissive by design — the app enforces the invariants, not the schema.
  • RLS was silently broken for a long time (stray ALL/true policies). Always verify pg_policies after schema changes.
  • Green API free tier caps distinct chats/month — customer WhatsApp delivery can stop while business alerts keep working.
  • Vercel Cron is daily-only here — keepalive & abandoned-checkout need an external scheduler (cron-job.org) to be genuinely useful. A stale keepalive heartbeat is now flagged on the admin Overview tab (§14); a stalled abandoned-checkout job is still silent.
  • ADMIN_SESSION_SECRET removed (2026-08-29) — it was vestigial (pre-DB signed-token design); no code ever read it. Deleted from the Vercel project env on 2026-08-29.
  • Category / label are plain text on products, not foreign keys — deleting a categories/labels row doesn’t cascade; products keep the string value.
  • discount_percent is display-only — never affects the charged amount.

Extending the system — playbooks

How to add the recurring things without breaking the invariants. Each playbook is the shortest safe path; follow the file it points at for the exact style. If a change spans two playbooks (e.g. a new setting that a cached query reads), do both.

Invariants that must always hold (full detail in §22 and AGENT.md): never trust the client at checkout (re-price, re-validate, re-check server-side); a new table gets RLS on with no anon policy, and rls.test.ts is re-run; side effects (WhatsApp / email / analytics) are try/catch + log, never blocking; 5xx bodies are generic via serverErrorResponse, 4xx messages are user-facing and fine; fail closed on missing security config; one shared constant over a “keep in sync” comment; docs/ARCHITECTURE.html (sections + a Change-log row) and the published artifact are updated before the batch is deployed — never after.

Add a migration

  • New file supabase/migrations/NNNN_short_description.sql, next number in sequence.
  • Every statement idempotent: add column if not exists, create table if not exists, insert … on conflict do nothing. It may be re-run against prod as a no-op.
  • Header comment: what + why + “run once in the Supabase SQL editor”.
  • New table → alter table X enable row level security; and (almost always) no policy — service-role only, like orders.
  • New function the server calls via rpc() → after revoke all … from public/anon/authenticated you must grant execute on function fn(argtypes) to service_role; explicitly — service_role inherits the PUBLIC grant, so the revoke strips it too and the rpc() call then fails. (Bit 0041, 0042 and 0043.)
  • Run it by hand in the Supabase dashboard (no CLI wired — see §24 / backlog #4). Add a row to §7. If it touched policies, run rls.test.ts against live.

Add an API route

  • app/api/<path>/route.ts, export async function GET/POST/…. Import supabaseAdmin (server-only) for DB access.
  • Public + mutating? Rate-limit with app/utils/rateLimit.ts (a new bucket name) and/or the OTP gate. If it writes a log-ish table, add the 2%-of-writes opportunistic prune (see rateLimit.ts / track-view).
  • Admin route? Put it under /api/admin/ — proxy.ts auto-applies the session check + cross-origin CSRF guard. After any write a cached storefront query reads, call revalidateTag(tag, "max").
  • 5xx → return serverErrorResponse("<context>", err[, publicMessage]). 4xx → plain NextResponse.json({ error: "…" }, { status: 400 }).
  • Add a row to the §11 table.

Add a cached storefront read

  • Add to app/utils/storeQueries.ts as unstable_cache(async (…) => {…}, ["unique-key"], { tags: […], revalidate: 86400 }).
  • Tags come from the fixed set: products, categories, coupons, reviews, orders, site-settings, labels. The admin write route that changes the underlying data must revalidateTag the same tag.
  • Needs to be fresher than a day (stock-like)? Do not cache it. Make it a force-dynamic + no-store route the client fetches on mount (pattern: LiveStock / /api/stock).
  • Never revalidateTag("products"/"orders") from the webhook — it schedules a full-storefront regeneration per sale (§16).

Add a site setting

  • It is one site_settings KV row. Seed a default in a migration (insert … on conflict do nothing).
  • Admin-editable? Add validation + an updates.push({ key, value }) branch in /api/admin/settings PATCH, a form field in the admin Settings tab, and revalidateTag("site-settings", "max").
  • Read it server-side through a getSiteSettings-style cached helper. Expose to the browser only by adding the key to PUBLIC_SETTING_KEYS in /api/settings — think before you do (operational values like last_keepalive_at stay server-side).
  • Structured value (a list, not a scalar): store one JSON string under one key and give it a dedicated pure module — a lenient, fail-closed parser for reads and a strict sanitiser (returns errors[]) for the admin PATCH branch. Unit-test it like coupons.ts/gst.ts. If it's not in PUBLIC_SETTING_KEYS but the storefront needs it, give it a narrow dedicated route (pattern: spend_tier_offer → app/utils/spendTierOffer.ts + GET /api/offer).

Add a WhatsApp notification

  • await sendWhatsappMessage(phone, text, imageUrl?) from app/utils/greenApi.ts, wrapped in try/catch + console.error. It silently no-ops without the three GREEN_API_* vars — never let a failed send block the triggering action.
  • Business-facing → BUSINESS_WHATSAPP_NUMBER. Customer-facing → the OTP-verified / pinned number, never a client-supplied one.
  • The free Green API tier caps distinct chats per month — assume customer-side delivery is best-effort.

Add a scheduled job

  • Route under app/api/cron/. Gate on CRON_SECRET bearer if set (pattern: keepalive / abandoned-checkout).
  • Vercel Hobby cron is daily-only — document that an external scheduler (cron-job.org) must hit it, and give it a health signal: stamp a site_settings timestamp on each run and surface staleness in the admin Overview (pattern: the keepalive heartbeat, §21).

Add an admin tab / panel

  • Add the key to ADMIN_TABS in app/admin/page.tsx + a { key, label } entry to the tab list. New tabs are their own component in app/admin/tabs/<Key>Tab.tsx (default export), dynamic(() => import(…), { ssr:false }) at the page’s module top, rendered as {activeTab === "<key>" && <KeyTab />}. All 7 existing tabs follow this shape (#16).
  • Shared data still loads in loadAll() (Promise.allSettled) on the page; the tab reads what it needs via useAdminData() (add the field to AdminData in app/admin/AdminDataContext.tsx and to the provider’s value). Tab-only state (form drafts, status strings) lives in the tab component. Use apiRequest from app/admin/lib/apiRequest.ts.
  • Compute stats client-side from already-loaded data where you can (pattern: the components/admin/* panels); CSV export via app/utils/downloadCsv.ts.
  • This file already carries pre-existing no-explicit-any / set-state-in-effect lint debt — match the surrounding style, don’t add new violations (derive from data in loadAll(), not with an impure call in render).

Touching the payment path

  • /api/razorpay, /api/razorpay-webhook, and the GST / coupon / signature utils they call — boundary #1 in AGENT.md. Written rationale, land behind tests, run next build + tsc + npm test, and never merge blind (no running app to exercise a real payment ⇒ it is a proposal, not done).
  • Both webhook callers stay idempotent: the SELECT payment_id guard and UNIQUE(payment_id) (migration 0037). Re-fetch from Razorpay’s API; never trust the request body. Trusted data is pinned into order.notes at creation time.
  • Anything new (stock reservation, …) ships behind a site_settings kill switch, seeded '0', with the webhook’s legacy path always intact so flipping it back is instant and needs no redeploy. Reserve before minting a payable order; a reservation error is a 500 with no order (fail closed).

Every batch, before deploy

  1. Group related changes; keep the diff surgical. One PR open at a time — merge and resync main before branching the next batch; stacked branches collide in IMPROVEMENTS.md and the Change-log table.
  2. Verify: npx next build (exit 0), npx tsc --noEmit, npm test, npx eslint <changed> (no new errors vs. the pre-existing baseline). Report the real output.
  3. Update the docs — this gates the deploy. Edit the affected § sections and add a dated Change-log row (IST time, files, how verified). Re-strip the skeleton and re-publish the artifact (https://claude.ai/code/artifact/85252c72-364e-44ee-80cf-710ae21d88cb, pass as url). Move shipped items to Done in IMPROVEMENTS.md.
  4. Only then ship. main is branch-protected — a direct git push origin main is rejected (GH013 … Required status check "verify"). Push the branch, open a PR, wait for the verify check green, re-verify the merged HEAD (next build + npm test), then merge the PR. Vercel deploys from the merge commit. (gh is not installed in the working environment — push the branch and have the owner merge, or hit the API with a token.)
  5. End with a short prioritised “what next” list; feed anything durable into IMPROVEMENTS.md.
End of reference. When you change the schema, a route contract, the caching strategy, or the checkout flow, update the matching section here in the same batch, before it deploys. This file is fully self-contained — no CDN, no scripts, no external assets.
