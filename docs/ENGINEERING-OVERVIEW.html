The stack

Chosen for a single-store storefront run by one person, not a team — every default leans toward “costs nothing extra to operate” over “infinitely scalable.”

FrameworkNext.js 16, App RouterReact 19, TypeScript in strict mode. Server Components for reads, Route Handlers for everything else — one framework, one deploy target.

System shape

Two rules shape almost everything else about how this is put together.

First: storefront reads are cached Server Components hitting the database directly. Writes, third-party calls, and anything that has to be live instead go through Route Handlers — a clean line between “can be a day stale” and “must be correct right now.”

Second: the browser never talks to the database for anything that matters. The public database key genuinely ships inside the page source — that's normal for this kind of architecture — so the database's own row-level security policies, not application code, are what actually decide what that key is allowed to see. More on that in Data & security.

Caching & performance

Every storefront read is wrapped in a tagged cache entry — products, categories, coupons each get their own tag. An admin edit invalidates just that tag; the next visitor to hit it triggers one cheap refetch. A completed sale deliberately does not invalidate the products cache — doing that would schedule a full-storefront regeneration on every single order. Instead, the numbers that change on every sale (stock, “N sold”) are read live, client-side, so the cached page underneath can stand for a full day.

The regeneration-quota incident

Product pages were originally statically generated with a 24-hour revalidate — one regeneration entry per product. That meant every deploy, and every product edit, regenerated all of them at once, and it quietly burned through most of the free hosting tier's monthly page-regeneration quota in a matter of weeks. The fix was to render product pages dynamically, per request, over the same cached database reads instead of pre-building them — a product page still costs on the order of tens of milliseconds of server time, just zero regeneration writes. Same speed for the shopper, a completely different cost profile for the host.

Images

Product photos are the single biggest weight on the page. Cards that only ever need a small preview — cart, wishlist, the catalogue grid — load a purpose-generated thumbnail instead of the full-resolution original, and uploaded images get a cache lifetime long enough to matter, since a product photo's storage path never changes once it's uploaded. Small decisions like these are the difference between a free storage tier lasting comfortably and not.

Worth knowing None of this needs a CDN or an image-optimization service turned on to work — it's plain HTTP caching and picking the right-sized asset for the context, which is available on every tier.

Checkout & payments

Checkout is a three-step guided flow — contact & verify, delivery, review & pay — driven by a small state machine rather than a pile of boolean flags. The machine's current phase is the current step; it holds the verification token and the OTP sub-state, but never the typed field values, so going back a step or a stale-verification rewind can never lose what someone's already typed.

Identity, checked server-side

Before payment, the phone number is verified with a one-time WhatsApp code, and the resulting token is single-use and time-boxed. The server re-checks that token at payment-creation time — a client that merely claims a number was verified earlier doesn't get past it.

A payment can be reported twice

A successful order gets reported to the server twice, independently — once by a fire-and-forget call the moment checkout succeeds, and again by the payment provider's own server-to-server callback, which retries on its own schedule. Both hit the same handler; each has to survive the other firing first. A unique constraint on the payment id at the database level, checked before either path writes anything, is what actually makes “exactly once” true rather than just “probably once.”

The last-unit race

Stock used to drop only after a payment cleared, which meant two shoppers could both successfully pay for the very last handmade piece before either checkout finished. A short-lived reservation now holds the requested quantity the moment checkout starts: one database function locks every line item in the cart, checks it against everything currently held by other in-progress checkouts, and grants the whole cart or none of it. The hold expires on its own if the sale never completes, so nothing has to sweep up after an abandoned cart by hand.

Never trusted from the client, on every single order: the price, the discount, the stock level, and whether the product is even still listed. All four are re-read from the database at the moment of payment, regardless of what the checkout page displayed a minute earlier.

Data & security

The public-facing database key ships inside every visitor's browser, so row-level security policies — not application code — are the real perimeter around anything that shouldn't be world-readable: orders, coupons, admin sessions, hidden products, unapproved reviews. That perimeter was silently broken for months, once, by a handful of leftover “allow everything” policies nobody remembered writing — database permissions are additive, so one forgotten permissive rule undoes every stricter one sitting next to it. It's re-asserted automatically now, on a daily schedule, against the live database, with an alert the instant anything drifts.

A few other standing rules

  • Fail closed on missing configuration. If a required security secret isn't set, the affected feature refuses to run rather than falling back to an insecure default.
  • Admin access needs two factors — a password and a time-based one-time code — with single-use backup codes for device loss, rate-limited login attempts, and a “sign out everywhere” control that revokes every active session at once.
  • Cross-origin admin writes are rejected at the edge before they reach any route handler, on top of the session cookie's own same-site restriction.
  • Error responses don't leak internals. A server failure returns a generic message to the caller; the real exception is logged server-side, never echoed back.

Code quality & process

Type safety earns its keep

The database client is generated straight from the live schema, which turns a whole class of silent bugs into compile errors instead: an id quietly compared as a string against a numeric column, a JSON column read as an untyped blob, a nullable field treated as guaranteed. A stale generated type fails the build outright rather than failing quietly in production.

Tests where it actually matters

Around 110 unit tests cover the parts that are expensive to get wrong — tax and discount math, signature verification, one-time codes, cart re-pricing, stock-reservation availability. The order-normalization tests include a deliberate round-trip check: feed it a well-formed order and assert the output comes back byte-for-byte identical, so a “safety” refactor can't quietly start mutating orders that were already fine. Anything touching the payment path is treated as a proposal, not a done thing, until it's been watched against real orders.

No shortcuts on the type checker

The codebase went from 246 lint problems down to zero real errors, and untyped escape-hatch usage from 174 occurrences to none — not by silencing the linter, but by writing out the actual shape of every payload the code handles. The handful of warnings still left on purpose each carry a comment explaining exactly why they're false positives, rather than being suppressed and forgotten.

Nothing ships undocumented

Every batch of work follows the same loop: make the change, verify it — typecheck, the full test suite, a real production build — update the reference documentation and write a dated changelog entry, and only then open it for review. Documentation is a precondition for shipping, not a follow-up task. The main branch is protected so nothing merges without that verification passing first, and changes are worked one at a time so two in-flight batches can never quietly overwrite each other's notes.

Comments explain the why, not the what

The codebase is deliberately over-commented in one specific way — not describing what a line does, but why it exists: the alternative that was rejected, the race condition being avoided, the trade-off behind a setting. A new non-obvious decision doesn't ship without a line naming what it deliberately isn't doing, and why.

Observability

Scheduled jobs stamp a heartbeat every time they run; if one goes quiet, a dashboard card turns amber instead of the failure being discovered a week later from a customer complaint. The security perimeter re-checks itself once a day against the live database and raises an alert the instant anything drifts — the same class of issue that, once, went unnoticed for months. The messaging gateway's own connection state is polled the same way, so a dropped session shows up on the dashboard instead of surfacing as a run of silently undelivered order confirmations.

That's the shape of it

A solo-run storefront, held together by defaults it doesn't have to think about twice.
